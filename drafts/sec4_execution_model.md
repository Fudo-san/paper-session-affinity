## 4.1 スケジューリング問題の定式化

タスク集合 T を、次の制約下で実行単位へ割り当てる問題として定式化する。

**制約**

1. **DAG 先行制約**: `dependencies` で表される先行関係を守る。
2. **write-set 排他**: 同時刻に同一ファイルへ書き込む2タスクを走らせない。
3. **セッション排他**: 1セッションで同時に2タスクを実行しない。
4. **モデル均質性**: 同一セッション内でモデルを切り替えない（§4.4）。

**目的関数**

```
min  Σ トークン費用 + λ · makespan
```

λ は費用と時間の交換レートであり、運用者が決める。本稿は λ を最適化する
スケジューラ（アームD）を提案しない。**λ の設計に必要なコストモデルを検証する**
のが本稿の位置づけである（§3）。

品質項（セッション汚染 → 手戻り確率）は本モデルの費用に算入せず、
§4.4 の失敗時セッション破棄の意味論と §6 の非劣性検証で扱う。

## 4.2 レーン継続ヒューリスティック（アームC）

**レーン ＝ write-scope の連結成分**である。

```
build_lanes(tasks, write_scope_for) -> LaneAssignment
```

- write-scope が交差する2タスクは同一レーン。
- 交差は**推移的に伝播**する（連結成分）。union-find で構成する。
- write-scope が空のタスクは単独レーン。
- レーンIDは、そのレーンに属する**最小の task_id** から決まる決定論的な値。
  実行順や dict の順序に依存しない（再現性のため）。

この定義の要点は、**安全性の要請とキャッシュ局所性が同じ区切りから出る**ことである。
write-scope が交差するタスクは制約2により**どのみち同時実行できない**。
ならば順番に流すしかなく、その順番を同一セッションに載せれば
継承履歴 H をキャッシュ経由で運べる（§3.4）。

**追加のコストを払わずにキャッシュ局所性を得られる**という主張がここにある。
本実験はこの主張を検証し、成立しない条件を特定した（§6.7、§8.2）。

### アームの実装上の差

実装は `session_mode` の1パラメータで切り替わる。

| アーム | `session_mode` | 挙動 |
|---|---|---|
| **B** | `"fresh"` | 従来どおり呼び出しごとに新規セッション。レーンを構成しない |
| **C** | `"lane"` | レーンを構成し、レーン内の2件目以降を `--resume` で継続 |

アームC では次の2つを守る。

- **レーン内の直列化**: 実行中のレーンに属するタスクは、前のタスクが終わるまで発行しない
  （`running_lanes` で管理）。
- **レーンをまたぐ並列は維持**: 別レーンのタスクは同時に走る。
  つまり C は「全直列」ではなく「**レーン内だけ直列**」である。

この点が本実験の代償を決める。依存関係で既に直列な形状（N）や、
1レーン1タスクの形状（W）では、C が追加で直列化するものが無い。
**依存が無いのに write-scope が交差する形状（Contended）でのみ、
並列度を捨てて文脈を再利用する交換が発生する**（§6.7）。

## 4.3 適応スケジューラ（アームD）

**park。本稿では扱わない。**

依存・競合・セッション親和性を同時に考慮する適応スケジューラは、
§3 で検証したコストモデルを目的関数とする設計になる。
モデルの検証が先行するのは方法論的必然であり、D は次稿の主題とする。

なお本実験の結果（§6）と M7 の所見（§8.1）は、D の設計制約を変える。
- ρ はクライアントから制御できないため、D の制御変数は g（境界ギャップ）と
  レーン構成に限られる。
- ρ は事後には観測できる（init の cache_read で分離）ため、
  **観測後に適応する**設計は可能である。これは D の拡張候補として残す。

## 4.4 失敗時の意味論・レーン長上限・モデル均質制約

### モデル均質制約

同一レーンでモデルが変わるとキャッシュが部分的に失われる。
M3 の実測では書き直しが履歴の **36〜46%**、費用は同一モデル継続の **2〜2.5倍**だった
（全損ではない。§3.2 の訂正記録）。

実装（`LaneSessions`）は、モデルが変わった場合に**セッションを引き継がず
新規扱いにして記録する**。`strict=True` なら例外を送出する。
既定を「黙って継続しない」にしてあるのは、**測定値を汚さないことを優先する**ためである。
切り替えの試行回数は `switch_attempts` に記録される。

### レーン長上限

§3.5 の損益分岐 H\* は、履歴が大きくなるほど継続が不利になることを示す。
したがってレーンには長さの上限が要る。

本稿では**上限を設けない**。理由は2つある。

1. 上限値 H\* は ρ に依存し、ρ はクライアントから制御・予測できない（§8.1）。
2. 予算付きレーン（アームC′）を検討したが、CT パイロットの実測で
   レーン先頭タスク終了時点の H が既に H\* を超えており、
   C′ はアームB へ縮退することが判明した（§7.5、Amendment A-2）。

上限の設計は、ρ の事後観測に基づく適応（§4.3）とあわせて次稿で扱う。

### 失敗時のセッション破棄

タスクが失敗した場合、そのセッションを継続に用いない。
失敗した文脈を後続タスクへ持ち込むと、汚染が伝播しうるためである。
本実験では受入失敗は1件のみで（§6.9）、この経路は実質的に発動していない。

## 4.5 pause/resume との整合

フレームワークは実行の中断・再開機構（`fwcore/checkpoint.py`、`fwcore/pause.py`）を持つ。
レーン継続はこれと直交する。

- 中断は**タスク境界**で起きる。レーン内のセッションIDは台帳（`LaneSessions`）に
  保持され、再開時に引き継がれる。
- ただし中断が長引けばキャッシュは cold になる。実測では約10.2分で cold へ遷移した（M2）。
  再開時に warm を期待してはならない。

本実験のドライバは、この点を**実験設計側で統制した**。run ごとに一意な nonce を
プロンプト先頭へ付け、run をまたぐキャッシュ共有を原理的に遮断している（§5.3）。

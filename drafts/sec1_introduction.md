## 段落1 — 問題

大規模言語モデルによるコーディングエージェントは、単一エージェントの対話的利用から、
複数エージェントが仕様を分担して並列に実装するマルチエージェント方式（MAS）へと
広がりつつある。並列化は壁時計時間を短縮する一方で、各エージェントが文脈を独立に
再取得するため、トークン消費——すなわち金銭コスト——を大幅に増加させる。
先行報告では、マルチエージェント構成が通常の対話の十数倍のトークンを消費する事例が
示されている［要引用: Anthropic 2025］。並列 MAS は本質的に「時間をトークンで買う」
取引であり、この交換レートを改善する仕組みは、MAS を実務コストの面で成立させる
鍵となる。

## 段落2 — 空白（先行研究に欠けているもの）

推論基盤を所有する環境では、この問題はサービング層で扱われてきた。プレフィックス
キャッシュを意識した実行順制御［要引用: SGLang］、アプリケーションの要求 DAG を
用いたサービング最適化［要引用: Parrot］などである。しかし商用 API の利用者は
モデルサーバにも KV キャッシュにも触れられない。一方、MAS フレームワーク研究
［要引用: MetaGPT, ChatDev, AutoGen］はコストを従属変数として報告するに留まり、
スケジューリングの目的関数に含めていない。リポジトリ上の競合制御やファイル所有権
に基づく割り当てを扱う近年の研究［要文献確認: CoAgent, CodeTeam 2026-06］も、
セッション継続という商用 API 唯一のキャッシュ経路をスケジューリング資源として
扱っていない——この統合が本研究の対象である。

## 段落3 — 主張とアプローチ

本研究は、推論基盤を変更できない商用コーディングエージェント上で、(i) タスク間の
依存関係、(ii) 計画時に宣言される書き込み範囲（write-scope）、(iii) セッション親和性
の3つを同時に考慮するクライアント側スケジューリング手法を提案する。中心となる
観察は単純である: 損益を支配するのはタスクの長さではなく境界のギャップと
キャッシュ TTL の大小関係であり、ギャップはスケジューラ自身が制御できる変数である
（§3）。したがって TTL は所与の制約ではなく、スケジューリング可能な資源となる。

## 段落4 — 貢献

1. 商用 API 上の MAS コード生成についての、観測可能な量だけで構成された
   コスト分解モデルと、セッション継続の損益分岐条件の導出（§3）
2. DAG 先行制約・write-set 排他・セッション/モデル切替コストを統合した
   実行モデルと、その適応スケジューラ（§4）
3. 同一仕様・対応付き設計による 4 方式の実証比較——単一エージェント継続 /
   MAS 新規セッション / MAS 単純レーン継続 / 提案（§6）
4. 探索的な負の結果の報告: 助言注入型の効率化と再帰的タスク分解が
   トークン効率をむしろ悪化させる条件（§7）

## 段落1 — 問題

大規模言語モデルによるコーディングエージェントは、単一エージェントの対話的利用から、
複数エージェントが仕様を分担して並列に実装するマルチエージェント方式（MAS）へと
広がりつつある。並列化は壁時計時間を短縮する一方で、各エージェントが文脈を独立に
再取得するため、トークン消費——すなわち金銭コスト——を大幅に増加させる。
先行報告では、マルチエージェント構成が通常の対話の十数倍のトークンを消費する事例が
示されている［要引用: Anthropic 2025］。並列 MAS は本質的に「時間をトークンで買う」
取引であり、この交換レートを改善する仕組みは、MAS を実務コストの面で成立させる
鍵となる。

## 段落2 — 空白（先行研究に欠けているもの）

推論基盤を所有する環境では、この問題はサービング層で扱われてきた。プレフィックス
キャッシュを意識した実行順制御［要引用: SGLang］、アプリケーションの要求 DAG を
用いたサービング最適化［要引用: Parrot］などである。しかし商用 API の利用者は
モデルサーバにも KV キャッシュにも触れられない。一方、MAS フレームワーク研究
［要引用: MetaGPT, ChatDev, AutoGen］はコストを従属変数として報告するに留まり、
スケジューリングの目的関数に含めていない。リポジトリ上の競合制御やファイル所有権に
基づく割り当てを扱う近年の研究［要引用: CoAgent 2606.15376, CodeTeam 2606.22082］も、
セッション継続という商用 API 唯一のキャッシュ経路をスケジューリング資源として
扱っていない。**そもそも、商用コーディングエージェント CLI の上でキャッシュが
実際にどう振る舞うのかを系統的に測った報告が存在しない**——スケジューリングの
議論はその測定の上にしか成り立たない。

## 段落3 — 本研究のアプローチ

本研究はまず、推論基盤を変更できない商用コーディングエージェント（Claude Code CLI）の
**キャッシュ経済を実測する**。次に、その実測から観測可能な量だけで構成された
コスト分解モデルを導出し、最後に、そのモデルが指す1つのスケジューリング方針——
write-scope 連結成分をレーンとし、レーン内でセッションを継続する——を
リポジトリ規模の実タスクで評価する。

測定の過程で、当初の見立てを**3度にわたって棄却**することになった。
(i) プロセス間の共有プレフィックスはキャッシュされない【A1】、
(ii) 継承履歴は以降のターンの書き込みを膨らませない【A6】、
(iii) 書き直しの発火は追加プロンプトのサイズでは決まらない【A6続報】。
これらはいずれも直感的にもっともらしく、実測なしには誤ったモデルを立てていた。
**本研究の第一の貢献は、この測定そのものである。**

## 段落4 — 貢献

1. **商用コーディングエージェント CLI のキャッシュ経済の実測**（§3.2）。
   プロセス間のプレフィックス非共有【A1】、セッション再開時の履歴読み出しと
   その費用比（中央値 1/11.1）【A3】、CLI 固定文脈の常時キャッシュ【A4】、
   resume が作ったキャッシュへの後続 fresh のヒット【A5】、
   書き込みが累積履歴に依存しないこと【A6】、
   公称 TTL（5分）が下限保証にすぎず実効生存が 6〜10 分であること【M2】。
   いずれも再現用スクリプトと生データを公開する。
2. **観測可能な量だけで構成されたコスト分解モデル**と、セッション継続の
   損益分岐条件の導出（§3.3〜3.5）。実測により2度改訂しており、
   モデルと測定の往復そのものを記録として残す。
3. **上記モデルが指す1つのスケジューリング方針の実証評価**（§4・§6）。
   write-scope 連結成分をレーンとするセッション継続を、同一仕様・対応付き設計で
   毎回新規セッションと比較する。**事前登録済みであり、効果が認められない場合も
   そのまま報告する。**
4. **探索的な負の結果**: 助言注入型の効率化と再帰的タスク分解が
   トークン効率をむしろ悪化させる条件（§7）。

> **v0.1 からの差分**: 旧 ② の「適応スケジューラ」は本稿の対象外（park）。
> 旧 ③ の「4方式の比較」は 2 アーム（B vs C）に縮小済み。
> 代わりに、旧 ① の中に埋もれていた実測群を独立した貢献として前に出した。

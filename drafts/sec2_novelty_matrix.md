## 本研究の主張（再掲）

推論基盤を変更できない商用コーディングエージェント上で、タスク依存・予測write-scope・
セッション親和性を**同時に**考慮するクライアント側スケジューリング。

## 新規性の判定（2026-07-05時点）

**空白は実在**: 「依存＋write-scope＋セッション親和性の同時最適化をクライアント側で行う」
研究は上記のいずれにも該当しない。特に:
- CodeTeam が所有権・依存までは到達（最近傍）だが、セッション/キャッシュ経済がない
- Don't Break the Cache がキャッシュ実測までは到達だが、単一エージェントで最適化しない
- サービング層（SGLang/Parrot/Autellix/Continuum/AGENTSERVESIM）は基盤所有が前提

**書き方の含意**:
1. §1段落2の空白の記述は本マトリクスの言い回しをそのまま使える
2. Continuum の「KV TTL＋tool時間予測」は §3 の g vs τ 洞察のサービング層版として
   明示的に対比すると論旨が立体的になる
3. Tokenomics の 59.4%/53.9% は §1 の動機の定量として引用
4. 宣言write-scopeのprecision/recall測定は、確認した全文献に見当たらない（独自性維持）

## 3. 用語の衝突（本稿で明示すべき）

**「session affinity」は2つの層で別の意味に使われている。**

- **サービング層の用法**（AGENTSERVESIM・SMetric・llm-d 等）: リクエストを、その KV キャッシュを
  保持する**GPUワーカーへルーティング**すること。
- **本稿の用法**: どのタスクを**どの会話セッションに入れるか**をクライアント側で決めること。

同じ語なので、§2 で**一段落を割いて明示的に区別する**必要がある。区別しないと
「既出」と誤読される。これは新規性の説明そのものに関わる。

## 5. 方法論上の失敗記録（重要）

ATM の PDF に対し「(a)〜(e) を扱っているか？」と**列挙して尋ねた**ところ、要約器は
**5点すべてを「扱っている」と回答**した。abstract 原文を確認すると、キャッシュ・セッション・
コストへの言及は**一切ない**。誘導的な質問が偽陽性を生んだ。

→ **規則: 文献判定は必ず abstract 原文（または本文の該当箇所）で確認する。**
要約器への質問は中立形（「何を解くか」「何を評価するか」）に限る。
この失敗は §2 の判定を一度は覆しかけた（＝論文の中止判断に直結しうる）。

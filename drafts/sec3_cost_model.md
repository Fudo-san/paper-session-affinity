# §3 Cost Model（ドラフト v0.1）

> 状態: Stage 1（データ収集前に確定できる理論部）。本文は実験結果に依存しない。
> 実測済みの事実には【A#】、未検証の仮定には【H#-A】タグを付す。
> 未検証仮定が棄却された場合の縮退先も明記する（§3.7）。

## 3.1 設定と記号

推論基盤（モデルサーバ・KVキャッシュ・バッチング）を制御できない商用コーディング
エージェント CLI を、クライアント側から呼び出してタスク列を実行する。課金は
プロバイダ報告のトークン使用量に基づく。

| 記号 | 意味 |
|---|---|
| p | 基準入力トークン単価（モデル別） |
| α_r, α_w | キャッシュ読み/書きの単価係数（本研究の対象APIでは α_r = 0.1, α_w = 1.25） |
| τ | キャッシュ TTL（同 5 分） |
| S | CLI が毎呼び出しに付与する固定コンテキスト（システムプロンプト等） |
| E_j | タスク j を新規セッションで開始した際の再探索コスト（文脈再取得のツール往復トークン） |
| H_i | タスク i 終了時点のセッション履歴サイズ（トークン） |
| K_j | タスク j 内の API 呼び出し回数 |
| g | 隣接する API 呼び出しの間隔（秒） |
| W_j | タスク j の本来の作業トークン（実装・編集・検証。実行形態に依存しない共通項） |

キャッシュは (a) プレフィックス一致でのみ効き、(b) モデル別である（モデル切替＝全損）。

## 3.2 実測アンカー（確定済みの事実）

- 【A1】別プロセスとして起動した fresh 呼び出し間では、ユーザープロンプトの共有
  プレフィックスはキャッシュされない。同一プレフィックス・別サフィックスの2呼び出しが、
  無関係なプレフィックスの呼び出しと完全に同一の usage（write 15,715 / read 14,679）を
  示した（2026-07-03 プローブ、n=3）。
  → 含意: 毎回新規セッションの実行方式（アームB）では、プロンプト整形による
  キャッシュ利得は構造的に得られない。クライアント側に残る唯一のキャッシュ経路は
  セッション継続である。
- 【A2】CLI の JSON 出力から usage 4区分（input / output / cache_creation / cache_read）と
  費用・session_id が呼び出し単位で取得できる。→ 本モデルの各項は直接観測可能。
- 【A3・成立（2026-07-05 resumeプローブ、n=1）】セッション再開（--resume）時、継承履歴 H は
  キャッシュ可能プレフィックスとして扱われる。3条件の実測:
  - P1 warm（g≈4秒）: cache_read = 28,850 ＝ 初回の cache_write(18,354)＋cache_read(10,496) と
    **完全一致**。費用 $0.1255 → $0.0099（**1/12.7**）。予測どおり成立。
  - P2 長ギャップ（g≈6.4分 > 公称TTL 5分）: **依然 warm**（cache_read=29,035, write=15）。
    → **公称TTLは下限保証であり、実際の生存はそれより長い**（この測定では≥6.4分）。
    真の cold 境界は未観測。残プローブ: 15/30/60分ギャップで消滅時刻を探る【データ待ち】
  - P3 モデル切替（haiku）: cache_creation = 18,744 ≒ 履歴全量の**書き直し**が発生。
    モデル切替＝キャッシュ全損を実証（レーンのモデル均質制約の直接根拠）。
    切替後の cache_read 10,690 は新モデル側の固定コンテキスト由来とみられる（要追検証）。

## 3.3 フレッシュ実行のコスト

タスク j を新規セッションで実行するとき:

    Cost_fresh(j) ≈ [S の carriage] + e_j + W_j
    e_j := E_j · (1 + (K_j − 1)·α_r)

E_j は初出時に全額、以降の呼び出しでは（タスク内の呼び出し間隔が τ 未満なら）
キャッシュ読みで運搬されるため、係数 (1 + (K−1)·α_r) を掛ける。
S は CLI 自身のキャッシュにより毎呼び出し α_r·S で読まれる（【A1】の実測で
S ≈ 14.7k トークンを確認）。壁時計時間には再探索のターン数分 t_E が加算される。

## 3.4 セッション継続のコスト

タスク i の直後にタスク j を同一セッションで実行するとき、継承履歴 H_i の運搬コストは
境界の「温度」で決まる（【A3】が成立する場合）:

    warm 境界（g ≤ τ, 同一モデル）:  c_warm ≈ K_j · α_r · H_i
    cold 境界（g > τ, 同一モデル）:  c_cold ≈ α_w·H_i + (K_j − 1)·α_r·H_i
    モデル切替:                      c_switch ≈ c_cold と同型（新モデルで全書き直し）
                                      ＋単価クラス・トークナイザ差の補正

タスク自身が生成する新規トークン（W 由来）の運搬は fresh でも継続でも同様に
発生するため、比較では一次近似で相殺される。

## 3.5 損益分岐（本モデルの中心的帰結）

継続が fresh より得になる条件（W, S を消去して）:

    warm:  K_j·α_r·H_i < e_j   ⇔   H_i < H*_warm = e_j / (K_j·α_r)
    cold:  (α_w + (K_j−1)·α_r)·H_i < e_j   ⇔   H_i < H*_cold = e_j / (α_w + (K_j−1)·α_r)

α_r = 0.1 のとき H*_warm は E の数倍（例: K=5 で 2.8·E）であり、warm 境界では
実用範囲のほぼ全域で継続が優位。一方 α_w = 1.25 のとき H*_cold ≈ 0.8·E（K=1）で、
長い履歴（H > E 程度）では fresh が優位に反転する。

**帰結（本論文の中心的洞察）**: 損益を支配する変数は「タスクの所要時間」ではなく
「境界のギャップ g と TTL τ の大小」である。そして g はスケジューラ自身が制御できる。
後続タスクを TTL 内に同一セッションへ投入できれば境界は warm に保てるため、
**TTL は与えられた制約ではなく、スケジューリング可能な資源になる**。
これが「セッション親和性をスケジューリング目的関数に含める」ことの理論的根拠である。

> 訂正メモ（自己訂正・論文には脚注不要）: 本研究の初期検討では「開発タスクは
> 10–30 分かかるため、レーン継続でも境界は概ね cold になる」と見立てていた。
> これは不正確である。境界温度を決めるのは前タスクの**最終**呼び出しと次タスクの
> **最初**の呼び出しの間隔であり、back-to-back にスケジュールされたレーンでは
> g ≈ 0 となる。cold 化は次の3条件でのみ生じる:
> (a) スケジューラ待ち（並列資源の競合・レーン間の待ち合わせ）
> (b) タスク内の τ 超の長時間ツール実行（例: 5分超の pytest）による内部 cold 化
> (c) Human チェックポイント等の外因性の待ち

## 3.6 スケジューラへの含意（§4への橋渡し）

タスク j をタスク i の後に割り当てる際のアークコスト:

    c(i → j | 同一セッション) = warm/cold 項（g の予測に依存）
    c(i → j | 新規セッション) = α_r·S·K_j + e_j

目的関数は  min Σ トークン費用 + λ·makespan、制約は (1) DAG 先行制約
(2) write-set 排他 (3) セッション排他（1セッション1実行）(4) モデル均質性
（切替=全損のため、単価クラスの異なるタスクは同一レーンに載せない）。
λ はコストと時間の交換レートであり、運用者が決める。

品質項（セッション汚染 → 手戻り確率）は本モデルでは費用に算入せず、
§4.4 の失敗時セッション破棄の意味論と §6 の非劣性検証で扱う。

## 3.7 検証可能な予測と縮退先

本モデルから次の観測可能な予測が出る（§6.1 の仮説へ流し込む）:

- P1: warm 再開の初回呼び出しは cache_read ≈ H を示す（【A3】の直接検証）
  → **2026-07-05 プローブで成立を確認**（cache_read が先行文脈と完全一致、費用1/12.7）
- P2: cold 再開の初回呼び出しは cache_creation ≈ H を示す
  → 6.4分ギャップでは cold にならず（TTLは下限保証）。真の消滅時刻は未観測で、
  モデルの cold 項は「g が実効生存時間を超えた場合」に読み替える。実効生存が長いほど
  レーンは有利（cold リスク3条件の (a)(c) が実務上さらに緩む）
- P3: back-to-back レーン（アームC/D）のトークン削減幅は、対応する fresh 実行の
  再探索コスト e の総和にほぼ一致する
- P4: 履歴が H* を超える長レーンでは削減が消失・反転する（レーン長上限の根拠）

【A3】が棄却された場合（resume 履歴がキャッシュされない場合）: §3.4–3.5 の
キャッシュ項は消えるが、E の回避（3.3）はセッション継続の定義そのものなので残る。
その場合、本論文の主張は cache-aware から session-affinity-aware（再探索回避）へ
縮退し、タイトルと §4 の目的関数から α 項を落とす。研究自体は成立する。

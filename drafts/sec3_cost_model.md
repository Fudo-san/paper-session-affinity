## 3.1 設定と記号

推論基盤（モデルサーバ・KVキャッシュ・バッチング）を制御できない商用コーディング
エージェント CLI を、クライアント側から呼び出してタスク列を実行する。課金は
プロバイダ報告のトークン使用量に基づく。

| 記号 | 意味 |
|---|---|
| p | 基準入力トークン単価（モデル別） |
| α_r, α_w | キャッシュ読み/書きの単価係数（本研究の対象APIでは α_r = 0.1, α_w = 1.25） |
| τ | キャッシュ TTL（同 5 分） |
| S | CLI が毎呼び出しに付与する固定コンテキスト（システムプロンプト等） |
| E_j | タスク j を新規セッションで開始した際の再探索コスト（文脈再取得のツール往復トークン） |
| H_i | タスク i 終了時点のセッション履歴サイズ（トークン） |
| K_j | タスク j 内の API 呼び出し回数 |
| g | 隣接する API 呼び出しの間隔（秒） |
| W_j | タスク j の本来の作業トークン（実装・編集・検証。実行形態に依存しない共通項） |

キャッシュは (a) プレフィックス一致でのみ効き、(b) モデル別である。

> **訂正（2026-08-03）**: 旧版はモデル切替を「全損」と書いていたが、実測は**部分損失**
> だった。切替後も CLI 固定コンテキスト S に相当する分は cache_read として計上される
> （【A4】）。「全損」は §3.3 の c_switch の記述（新モデルで全書き直し）とも整合しない。
> 以後は「モデル別であり、切替時は履歴 H 相当が書き直しになる」と書く。

## 3.3 フレッシュ実行のコスト（2026-07-31 改訂）

タスク j を新規セッションで実行するとき:

    Cost_fresh(j) ≈ [S の carriage] + e_j + W_j
    e_j := E_j · (1 + (K_j − 1)·α_r)

E_j は初出時に全額、以降の呼び出しでは（タスク内の呼び出し間隔が τ 未満なら）
キャッシュ読みで運搬されるため、係数 (1 + (K−1)·α_r) を掛ける。
S は CLI 自身のキャッシュにより毎呼び出し α_r·S で読まれる（【A4】の実測で
S ≈ **21.6k** トークン。当初 A1 から推定した 14.7k を更新）。
壁時計時間には再探索のターン数分 t_E が加算される。

**クロスセッション割引の有無（2026-07-31 M4 で決着）**: 一時、独立 fresh セッション間でも
探索プレフィックスがキャッシュにヒットする可能性を疑い、割引率 γ を導入した。
**M4（n=3）で γ = 1（割引なし）が確定**したため、γ 項は落とし当初の形へ戻す。
アームBに構造的なキャッシュ利得は存在しない。

ただし **【A5】の汚染経路は残る**: アームCの resume が作ったキャッシュに、直後の
アームBの fresh がヒットしうる。これはモデルの項ではなく**実験設計で統制すべき交絡**であり、
S6 の実行スケジュール（同一 spec の B/C の離隔）で扱う。

## 3.4 セッション継続のコスト

タスク i の直後にタスク j を同一セッションで実行するとき、継承履歴 H_i の運搬コストは
**2つの独立した条件**で決まる（v0.3・2026-08-04 改訂）:

1. **境界の温度**（g と TTL τ の大小。【A3】【M2】）
2. **初回 resume の追加プロンプト量**（【A6】）— warm でも書き直しを起こしうる

書き直しの有無を指示変数 `ρ ∈ {0,1}` で表す（ρ=1: 履歴 H が書き直される）。
ρ=1 になるのは (i) cold 境界、または (ii) warm でも追加プロンプトが大きいとき。

    c_cont ≈ ρ·α_w·H_i + (K_j − ρ)·α_r·H_i

    ρ=0（warm かつ追加小）:  c ≈ K_j · α_r · H_i
    ρ=1（cold または追加大）: c ≈ α_w·H_i + (K_j − 1)·α_r·H_i

    モデル切替:
    モデル切替:                      c_switch ≈ c_cold と同型だが**部分損失**。
                                      実測（M3 n=2）では書き直しは H の 36〜46% にとどまり、
                                      残りは cache_read される。cost比は同一モデル warm の
                                      約2〜2.5倍、fresh init の約1/5。
                                      ＋単価クラス・トークナイザ差の補正

タスク自身が生成する新規トークン（W 由来）の運搬は fresh でも継続でも同様に
発生するため、比較では一次近似で相殺される。

## 3.5 損益分岐（本モデルの中心的帰結）

継続が fresh より得になる条件（W, S を消去して）。§3.4 の ρ を用いて一本化すると:

    (ρ·α_w + (K_j − ρ)·α_r)·H_i < e_j
      ⇔  H_i < H* = e_j / (ρ·α_w + (K_j − ρ)·α_r)

    ρ=0（warm かつ追加小）: H*₀ = e_j / (K_j·α_r)
    ρ=1（cold または追加大）: H*₁ = e_j / (α_w + (K_j−1)·α_r)

α_r = 0.1 のとき H*₀ は E の数倍（例: K=5 で 2.0·E）であり、この経路では実用範囲の
ほぼ全域で継続が優位。一方 α_w = 1.25 のとき、K=10 で H*₁ ≈ 0.47·E、K=5 で ≈ 0.59·E。
**ρ=1 は閾値をおおよそ半分にする。**

**【A6】がもたらす含意（v0.3 で追加）**: ρ は境界温度だけでは決まらない。
即時 resume（g≈0）であっても、初回の追加プロンプトが大きければ ρ=1 になる。
developer タスクの初回プロンプトは task JSON ＋依存サマリーで数千〜1万文字あり、
**実運用のレーン継続は ρ=1 側で動いている可能性が高い**。
したがって H* の実効値は H*₁ ≈ 0.5·E 前後と見積もるべきで、
「warm に保てば安泰」という v0.2 までの含意は**過度に楽観的**だった。

**ρ は制御できる可能性がある（C′ の設計に直結）**: 書き直しの閾値は 300〜20,000 文字の
間にある。初回プロンプトを閾値未満に抑えられれば ρ=0 を維持でき、H* を倍にできる。
閾値の特定は費用対効果の高い追加測定である（`未記入` §に記載）。

**帰結（本論文の中心的洞察）**: 損益を支配する変数は「タスクの所要時間」ではなく
「境界のギャップ g と TTL τ の大小」である。そして g はスケジューラ自身が制御できる。
後続タスクを TTL 内に同一セッションへ投入できれば境界は warm に保てるため、
**TTL は与えられた制約ではなく、スケジューリング可能な資源になる**。
これが「セッション親和性をスケジューリング目的関数に含める」ことの理論的根拠である。

> 訂正メモ（自己訂正・論文には脚注不要）: 本研究の初期検討では「開発タスクは
> 10–30 分かかるため、レーン継続でも境界は概ね cold になる」と見立てていた。
> これは不正確である。境界温度を決めるのは前タスクの**最終**呼び出しと次タスクの
> **最初**の呼び出しの間隔であり、back-to-back にスケジュールされたレーンでは
> g ≈ 0 となる。cold 化は次の3条件でのみ生じる:
> (a) スケジューラ待ち（並列資源の競合・レーン間の待ち合わせ）
> (b) タスク内の τ 超の長時間ツール実行（例: 5分超の pytest）による内部 cold 化
> (c) Human チェックポイント等の外因性の待ち

## 3.6 スケジューラへの含意（§4への橋渡し）

タスク j をタスク i の後に割り当てる際のアークコスト:

    c(i → j | 同一セッション) = warm/cold 項（g の予測に依存）
    c(i → j | 新規セッション) = α_r·S·K_j + e_j

目的関数は  min Σ トークン費用 + λ·makespan、制約は (1) DAG 先行制約
(2) write-set 排他 (3) セッション排他（1セッション1実行）(4) モデル均質性
（切替は部分損失だが同一モデル warm の2〜2.5倍の罰則があるため、単価クラスの
異なるタスクは同一レーンに載せない）。
λ はコストと時間の交換レートであり、運用者が決める。

品質項（セッション汚染 → 手戻り確率）は本モデルでは費用に算入せず、
§4.4 の失敗時セッション破棄の意味論と §6 の非劣性検証で扱う。

## 3.7 検証可能な予測と縮退先

本モデルから次の観測可能な予測が出る（§6.1 の仮説へ流し込む）:

- P1: warm 再開の初回呼び出しは cache_read ≈ H を示す（【A3】の直接検証）
  → **成立を確認**（cache_read が先行文脈と完全一致）。費用比は M1 n=3 で**中央値 1/11.1、範囲 1/10.3〜1/13.4**。初出の 1/12.7 は n=1 の値で分布の楽観側の端にあたるため、以後は中央値と範囲で記す。
- P2: cold 再開の初回呼び出しは cache_creation ≈ H を示す
  → 6.4分ギャップでは cold にならず（TTLは下限保証）。真の消滅時刻は未観測で、
  モデルの cold 項は「g が実効生存時間を超えた場合」に読み替える。実効生存が長いほど
  レーンは有利（cold リスク3条件の (a)(c) が実務上さらに緩む）
- P3: back-to-back レーン（アームC/D）のトークン削減幅は、対応する fresh 実行の
  再探索コスト e の総和にほぼ一致する
- P4: 履歴が H* を超える長レーンでは削減が消失・反転する（レーン長上限の根拠）

【A3】が棄却された場合（resume 履歴がキャッシュされない場合）: §3.4–3.5 の
キャッシュ項は消えるが、E の回避（3.3）はセッション継続の定義そのものなので残る。
その場合、本論文の主張は cache-aware から session-affinity-aware（再探索回避）へ
縮退し、タイトルと §4 の目的関数から α 項を落とす。研究自体は成立する。

## 3.8 仕様単位への合算と単位の確定（v0.2 で新設。H4(b) の前提）

旧版はタスク単位の `Cost_fresh(j)` と境界単位の `c_warm/cold` までしか定めておらず、
**仕様単位の予測 r̂ を計算する規則が存在しなかった**。H4(b) は「仕様ごとの費用比
r = Cost_C/Cost_B が予測 r̂ と ±25% 以内」を求めるので、ここを埋めない限り
H4(b) は判定できない。以下を `formula_id = sec3-spec-cost-v1` として固定する。

### 3.8.1 合算式

仕様 s のタスク集合を T_s、レーン分割を L_s（write-scope 連結成分。§4.2）とする。

```
Ĉ_B,s = Σ_{j∈T_s} Ĉ_fresh(j)

Ĉ_C,s = Σ_{l∈L_s} [ Ĉ_fresh(first(l)) + Σ_{i→j ∈ l} Ĉ_resume(i,j) ]

r̂_s  = Ĉ_C,s / Ĉ_B,s
```

**各レーンの最初のタスクは fresh 扱い、2件目以降は resume 扱い**と固定する。
レーン内の順序は `build_lanes` が返す決定論的順序（最小 task_id 由来）に従う。
レーンをまたぐ順序は r̂ に影響しない（合算が線形のため）。

### 3.8.2 単位: すべて USD で予測する

旧版は基準入力単価 p だけを持ち、E・H・W を「トークン」と書いていた。
これでは出力と入力を同じ価格で扱うことになり、実測 USD と突き合わせられない。
**入出力・キャッシュ区分をそれぞれ予測して USD へ換算する**（監査しやすいため。
「基準入力トークン換算量」に潰す方式は、換算係数が隠れるので採らない）。

必要な単価は4区分:

| 区分 | 記号 |
|---|---|
| 通常入力 | p_in |
| 出力 | p_out |
| cache read | p_in · α_r（α_r = 0.1） |
| cache creation | p_in · α_w（α_w = 1.25） |

単価の出典と取得日を `model_predictions.json` の `constants.pricing_source` に記録する。
**キャッシュ保持時間別の write 単価**（5分/1時間）が存在する場合は区分を分ける。
実測で `cache_creation.ephemeral_1h_input_tokens` が観測されているため、
この分岐は実在する。予測時にどちらを仮定したかを明記する。

### 3.8.3 較正に必要な量と、その取得方法

`E_j`・`H_i`・`W_j` は**タスク単位の合計 usage からは識別できない**（【A2】訂正記録）。
`--output-format stream-json --verbose` を使えば per-turn の usage が取れ、
その総和は result の合計と一致する。これを較正に使う。

| 量 | 取得方法 |
|---|---|
| K_j | assistant イベント数（`num_turns` とも一致） |
| H_i | タスク i の最終ターン時点の累積コンテキスト |
| E_j | fresh 開始時、**作業に入る前**の文脈再取得ターン群のトークン |
| W_j | 残余（総トークン − S 相当 − E_j） |

E_j と W_j の境界は観測から自明でないため、操作的定義を先に固定する:
**「最初に編集系ツール（Write/Edit）を呼ぶまでのターン群を E、以降を W とする」**。
この定義は恣意的である。恣意性は Limitations に明記し、
境界を1ターンずらした場合の感度分析を副次として報告する。

### 3.8.4 較正データの独立性（H4(b) を検証たらしめる条件）

**パイロットの C/B 費用比を r̂ の作成に使わない。** 使えば H4(b) は
「モデルの検証」ではなく「パイロット比の再現性確認」になる。

- 較正は**独立した較正キャンペーン**、または**パイロットの B 側のみ**から行う。
- r̂ は手入力せず、**コミット済みのスクリプトが較正データから計算**する。
  手入力を禁じるのは、無意識の適合の余地を式が表現できる範囲に閉じ込めるため。
- 較正データ・算出コード・`model_predictions.json` を**同時にコミット**する。
- その後に本実験を開始する。

> **開示（2026-08-03）**: 本文書の執筆者は、パイロットの集計値
> （6仕様中5仕様で C が高い、平均 +12.7%）を**既に見ている**。これは取り消せない。
> 緩和策は上記のとおり r̂ を機械計算に限定することだが、
> 完全な盲検ではない。この事実を Limitations に明記する。

## 5.1 基盤

実験は既存の MAS フレームワーク上で行った。**本研究のために新しい実行基盤を
作っていない。** アームB（呼び出しごと新規セッション）はフレームワークの
既定動作そのものであり、アームC は `session_mode` の1パラメータで有効化される（§4.2）。

役割を混同しないよう明記する。

| 役割 | 実体 |
|---|---|
| **ハーネス**（実験を回す側） | MAS フレームワーク＋`harness/` のドライバ |
| **対象リポジトリ**（実験される側） | `square-media`（Python・受入テスト付き） |

対象リポジトリは3つのコミットで固定した。いずれも**受入テストが存在し
実装が存在しない**点である（`d4449a0` / `3be3676` / `6f5b695`）。
実験は worktree でその commit をチェックアウトするため、
対象リポジトリの main が進んでも実験は影響を受けない。

## 5.2 計装

### 呼び出し単位（`calls.jsonl`）

CLI 1呼び出しにつき1行を追記する。記録項目:

| 分類 | 項目 |
|---|---|
| 識別 | `spec` `arm` `rep` `task_id` `agent` `session_id` `iso` |
| 実行 | `backend` `returncode` `wall_s` `error` `resumed` |
| 環境 | `model` `models_used` `cli_version` |
| usage | `input_tokens` `output_tokens` `cache_read_tokens` `cache_creation_tokens` `cost_usd` |
| **per-turn** | `num_turns` `peak_context_tokens` `turns[]` |

`model` の取得には注意が要る。**CLI 応答にトップレベルの `model` キーは無く、
`modelUsage` の「キー」がモデル名である。** 実装は `modelUsage` を費用で降順に見て
主モデルを決める。

### per-turn 計装（A11）

`--output-format json` はタスク単位の**合計**しか返さない。実測では
`num_turns=3` に対し `usage.iterations` が1件しか無く、合計 cache_read 70,744 の
うち 44,000 の帰属が不明だった。これでは §3 の E（再探索）と W（作業）を分離できない。

`--output-format stream-json --verbose` は assistant イベントごとに usage を返し、
**その総和が result の合計と正確に一致する**（実測: 26,510 + 26,510 = 53,020）。
本実験はこちらを用い、`turns[]` に per-turn の
`message_id` / `input_tokens` / `output_tokens_partial` / `cache_read_tokens` /
`cache_creation_tokens` を記録した。`peak_context_tokens` は H の軌跡に対応する。

### run 単位（`run.json`）と台帳（`run_ledger_main.csv`）

run 単位では `usage_actual`（合計）・`accepted`（受入の二値）・`verify_tail`・
`wall_s`・`seed`・`cli_version` を残す。
台帳は**追記のみ・改変禁止**とし、破棄した run の行も残す（`exclusion_rules` §5）。
有効データはディスク上の `run.json` 側を正とする。

## 5.3 決定論優先の設計原則

測定を汚す経路を、実行前に構造で塞ぐ方針を採った。

**① run ごとの一意プレフィックス（nonce）**

【A5】として観測した汚染経路 —— resume が作ったキャッシュに後続の fresh 呼び出しが
接頭辞一致でヒットする —— を遮断する。プロンプト先頭に run 固有の文字列を置くため、
プレフィックスが最初のトークンから食い違い、**TTL に関係なくキャッシュ共有が
原理的に成立しない**。run 内では同一値なので、アームC の resume（session_id で継続）は
影響を受けない。

**② provider フォールバックの遮断**

フレームワークは既定で primary 失敗時に別 provider へ落ちる。実験中にこれが起きると、
フォールバック先が `--resume` を持たないため**アームC が黙ってアームB 相当に成り下がり**、
モデルも変わって費用が比較不能になる。しかも記録上は成功した run に見える。
実験中は `fallback=None` とし、落ちたら中断させる。

**③ 空振り・部分実行の検出**

provider 枯渇時、フレームワークは例外を出さずに戻る。その結果
`cost=0`・トークン0 の run が「完了」として台帳に載りうる。さらに
4タスク中1タスクだけ実行できた run も `cost>0` になり、有効な観測として
集計へ入ってしまう（実際に発生し、相対差を ±40〜85% 動かしていた）。

有効性の条件を「`cost>0` **かつ** 計画したタスク数だけ呼び出しがある」とし、
満たさない run は中断して記録する。**受入に落ちること自体は正当な観測**なので
`accepted` の真偽は条件に含めない。

**④ 対が窓をまたぐことの検出**

利用上限で反復が途中終了すると、片アームだけ完了した対が残りうる。そのまま再開すると
完了済みアームは飛ばされ、もう一方だけが別の時間帯で走る。
`exclusion_rules` §3 は対ごとの再実行を定めているため、検出したら**停止して人間に返す**。
黙って進めない（`--allow-split-pairs` の明示が要る）。

**⑤ 隔離**

run ごとに独立した worktree を用意し、相互汚染を防ぐ。
実験専用の sprint id を用い、対象リポジトリの実在スプリント（完了フラグや過去の成果物を
含む）と衝突させない。

## 5.4 実装していないもの（明示）

OUTLINE v0.1 の §5.2 は次を計装項目として挙げていたが、**実装していない**。

- **影git による実 write-set の取得**: 宣言された write-scope と実際の書き込みの
  差分（`scope_drift`、write-scope の precision/recall）を測る計装。
  §6.4 では副次指標として挙げていたが、本実験では取得していない。
  したがって scope_drift と write-scope の precision/recall は**報告しない**。

- **審判LLM（`judge.py`）**: 受入判定は対象リポジトリの pytest の
  終了コードで行っており、LLM による採点は用いていない。
  判定が機械的・決定論的である点は本実験の強みだが、
  「受入テストで表現できる品質」しか測れていないという限界でもある（§8.8）。

## 5.5 テストと検証

| 対象 | 件数 | 性質 |
|---|---|---|
| フレームワーク（レーン構成・resume の引き回し） | 48 | 実装の回帰 |
| 分析（統計プリミティブ） | 29 | **合成データのみ** |

分析テストが合成データのみである点は意図的である。実データで検証すると
(1) 手法を結果に合わせて調整でき、(2) 本実験の結果を先に覗くことになる。
「全対が同符号なら p は下限に張り付く」「対称なら有意にならない」
「データを定数だけずらせば区間も同じだけずれる」など、
**答えが分かっている入力**に対する挙動だけを確かめている。

この方針は実際に設計の誤りを1件捕まえた。当初、置換検定の統計量を中央値にする
予定だったが、合成データで**中央値が符号反転検定の統計量として機能しない**ことが
判明した（差が全て同じ大きさの20対で p が 0.82 まで上がる）。
有意性は平均、実質性は中央値と役割で使い分ける形へ改めた
（`PRE_ANALYSIS_DECISIONS.md` 決定B）。**実データを見る前に見つかった**ため、
結果に合わせた選択ではないことをコミット順序で示せる。

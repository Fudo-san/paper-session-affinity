# パイロット結果 2026-08-02

## 位置づけ

`protocol/` は FROZEN。パイロットが決めてよいのは**反復数 N だけ**である。
以下の相対差の値を根拠に、仮説・アーム・指標・閾値・除外規則を変更してはならない。

## 結論: N = 14

事前登録（`pre_pilot_decisions.md` 決定3）で先に固定した式に、パイロットの
18対を入れた結果。

```
相対差 d = (C - B)/B
n = 18   平均 +12.7%   SD 26.6%
N = (1.96 + 0.84)^2 * 0.266^2 / 0.20^2 = 13.9  ->  切り上げ 14
```

**上限20の内側**なので撤退条件には当たらない。本実験は実施可能である。

## 観察（結果ではない）

**6仕様のうち5仕様で符号が正**、すなわちレーン継続（C）の方が高い。
仮説（継続すれば安くなる）とは逆向きである。負なのは `n_db_chain` だけ。

これはパイロットであり、この向きを結論として扱わない。ただし本実験で
「効果なし」または「逆向き」が出る可能性を、あらかじめ想定しておくべきである。
事前登録済みなので、そう出た場合もそのまま報告できる。

ばらつきが大きい理由は、エージェントが何ターン回すかが run ごとに揺れるため。
同一タスクを同一初期状態から新規セッションで走らせても cost が 17〜35% ぶれる
ことを、スモークとパイロットの両方で観測している。

## 消費量の実測（本実験の設計に直結）

| 項目 | 実測 |
|---|---|
| 1ランあたり cache_read | 約 110万トークン |
| 1タスクあたり cache_read | 中央値 438,000 トークン |
| パイロット総消費 | 3,350万トークン |
| 5時間窓で回せるラン数 | **約18ラン**（新鮮な窓で実測） |

1タスク438,000トークンの主因は、対象ファイルが大きいこと（`src/db.py` は
1,100行超）。エージェントが一度読むと、以降の全ターンがその内容を読み直す。
タスク記述は関数シグネチャまで書いてあり、探索を減らす方向に既に効いている。
仕様の書き方の問題ではなく、実在リポジトリでエージェントを回すことに内在する。

通常のスプリントが上限に当たらないのは、development_phase を1回しか回さない
ため。本実験はそれを168回回す。

## 本実験の構成

| 項目 | 値 |
|---|---|
| 規模 | 6仕様 × 14反復 × 2アーム = **168ラン** |
| 費用 | 概算 **$190**（パイロット実績 $1.12/ラン） |
| 実行単位 | **1窓 = 1反復（12ラン）**、上限に当たる前に自分から止める |
| 所要 | 14窓 × 5時間 = **約70時間（3日）** |

### 窓をまたぐことの可否

またいでよい。**条件は1つ、同じ対（同一 spec の B と C）を同じ窓に収めること。**
対が窓をまたぐと、その対だけ窓の影響と交絡する。反復が別の窓にあるのは問題ない。
ABBA で反復ごとにアーム順を反転しているため、窓の影響はアーム間で相殺される。

上限に当たるまで走らせてはならない。当たった位置で対が割れる。
1反復（12ラン）流したら自分から止める。実測18ランに対して3割の余裕がある。

## パイロット遂行中に見つけて直した欠陥

いずれも「記録上は成功した run」に見えるもので、気付かなければ本実験のデータを
汚染していた。

1. **空振りを成功として記録** — provider 枯渇でも例外が出ず、cost=0・wall 3秒の
   run が completed になり、残り25本を空回しして12分の cooldown を2回眠った。
2. **実験用スプリントが実在スプリントと衝突** — `sprints/sprint_1/` には対象
   リポジトリの `sprint_done.json` と過去の `results/` が入っていた。`sprint_exp` へ分離。
3. **provider フォールバックがアームCを黙って無効化** — primary 失敗時に codex へ
   落ちる。`supports_resume=False` なのでアームCがアームB相当に成り下がり、
   モデルも変わってコストが比較不能になる。実験中は `fallback=None`。
4. **A5 汚染を相殺で済ませていた** — 12分 cooldown と ABBA は打ち消しであって
   無効化ではない。run ごとの nonce をプロンプト先頭へ入れて原理的に遮断した。
5. **バックエンド失敗の理由が空欄** — CLI は stderr を空のまま stdout の JSON に
   理由を書いて非ゼロ終了する。stdout 側も拾うようにした。これにより
   「session limit · resets 2:20pm」という出所の確かな情報が読めるようになった。
6. **スキップと cooldown の順序** — 既に終わった run のために12分眠ってから
   飛ばしていた。再開時に72分の空待ちになる。
7. **部分実行を有効な観測として集計** — 有効性の判定が cost>0 だけだったため、
   4タスク中1タスクしか実行できなかった run が集計に入っていた。2件あり、
   しかも逆方向に歪めていた（一方は C を −84.7%、もう一方は B を +46.5%）。
   **この2点だけで SD が 20.2% から 32.1% に膨らみ、N が撤退ライン20を超えていた。**
   判定の欠陥が結論そのものを反転させかけた例である。

再実行率 2/18 = 11%。事前登録の停止閾値20%の内側。

## 運用上の記録

- `.mk2/quota_state.json` はプロバイダの標準エラー出力を**文字列マッチ**して

  停止理由を調べるときは、このファイルと直接の CLI 呼び出しを突き合わせること。

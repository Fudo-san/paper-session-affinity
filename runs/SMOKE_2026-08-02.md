## 観察1: この1回では C が安くならなかった

C は B より **6.4% 高い**。cache_creation も C の方が多い（78,759 vs 71,055、+10.8%）。

考えられる機序（**仮説であり、本記録では検証しない**）: resume は T-17101 の履歴を
まるごと T-17102 へ持ち込む。持ち込んだ分だけキャッシュすべきプレフィックスが伸び、
`α_w=1.25` で課金される cache_creation が増える。節約は `α_r=0.1` 側にしか効かないため、
履歴が大きいと差し引きで不利になりうる。

cooldown=0 なので、後に走った C は B が残したキャッシュを踏めた可能性がある（A5）。
それは C を**安く**する方向の汚染であり、それでも C が高い。
つまりこの向きの観察は汚染では説明されない。

## 観察2: 同一タスク・同一初期状態でも run 間のばらつきが大きい（設計に直結）

B の T-17101 と C の T-17101 は、**同じタスクを同じ commit から新規セッションで**
走らせたものである。条件は揃っている。それでも:

- cache_read: 435,810 vs 591,772（**+35.8%**）
- cost: 0.3737 vs 0.4383（**+17.3%**）

エージェントが何ターン回すかが run ごとに揺れるためと考えられる。

**これは N の決定に直接効く。** 事前登録の「実質的削減」閾値は 20% であり、
上の素のばらつき 17% とほぼ同じ桁である。反復2回では検出力が全く足りない。
S5 パイロットでこのばらつきを spec ごとに実測し、そこから N を決める必要がある。

事前登録上、パイロットで決めてよいのは N だけである。閾値・指標・アームは動かさない。

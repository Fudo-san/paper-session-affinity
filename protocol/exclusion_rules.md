# 事前登録: 除外・再実行規則

> 作成: 2026-07-31 / status: **FROZEN v1.0**（2026-07-31 承認・凍結。本実験開始後の変更禁止）
> 原則: **アームの結果を見てから除外を決めることを禁止する。**
> 除外できるのはインフラ起因のみ、かつ対応ペア単位。

## 1. 除外可能（＝再実行の対象）

以下が run 中に発生した場合、その run は「無効」とし再実行する:

- ベンダー側障害（5xx・タイムアウト・サービス停止）
- rate limit / quota 枯渇による中断
- CLI・ハーネスのクラッシュ（タスク内容に起因しないもの）
- 計装の欠損（calls.jsonl が不完全で費用・トークンが復元不能）
- 電源・OS・ネットワーク障害

## 2. 除外不可（＝結果として計上する）

以下は**アームの成績そのもの**であり、除外・再実行しない:

- モデルの拒否・无関係な出力・不正な patch
- 受入テストの失敗
- 設定 max-steps 内でのステップ使い切り・タイムアウト
- scope violation（宣言 write-scope 外への書き込み試行）
- 修正サイクルの多発

## 3. 再実行の規則

- 単位: **spec × rep のペア（B・C両方）を同一時間帯枠で再実行**する（対応維持のため、
  無効になったのが片アームでも両方やり直す）。
- 上限: 同一 spec×rep につきインフラ起因の再実行は **1回まで**。2回目のインフラ障害が
  出た場合はその spec×rep を欠測として記録し、補充しない。
- 記録: すべての再実行を `run_ledger.csv` に理由つきで記録する。
- **停止条件**: インフラ起因の再実行率が全 run の **20%** を超えたら実験を停止し、
  原因（時間帯・ベンダー状態・ハーネス）を調査してから再開する。再開時は Amendment Log に記録。

## 4. 交絡の統制

- モデル ID・CLI バージョンを固定し、**毎 run 記録**する。
- キャンペーン中にバージョンドリフトが発生した場合: そのブロック以降は**別層（stratum）**
  として分離報告するか、ブロック全体を再実行する。混ぜて集計しない。
- アームの実行は時間帯交互配置（ABBA）。キャッシュ挙動・負荷の時刻依存を
  片アームに偏らせない。

## 5. 外れ値・データの扱い

- **事後の外れ値除外は行わない。** 全数を報告する。
- 極端値を除いた感度分析は**副次**としてのみ許可（主要判定には使わない）。
- `runs/` 配下の生データ（calls.jsonl 等）と `run_ledger.csv` は追記のみ・改変禁止。
- 分析スクリプトはバージョン管理下に置き、主要判定に使った版を Results に明記する。

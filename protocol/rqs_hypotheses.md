## 2. 指標定義（§6.4 の確定リストから役割を指定）

| 役割 | 指標 | 定義 |
|---|---|---|
| **主要評価（RQ1）** | 仕様×反復あたり総費用 USD | ベンダー報告値（input / output / cache_read / cache_write を各単価で加重） |
| **共同ゲート（RQ2）** | 壁時計時間 | 仕様の投入から受入判定完了まで |
| **共同ゲート（RQ3）** | 受入全通過率 | 仕様×反復ごとに受入テスト全通過なら1、それ以外0 |
| 副次 | トークン内訳・scope_drift・修正サイクル数・write-scope precision/recall | 報告のみ。主張の根拠にしない |

## 3. 仮説と判定規則

### H1（RQ1・費用）

- **予測**: C の費用は B より低い。削減幅は再探索コスト e の総和に近い（§3.5 P3）。
- **判定**: 対応付き置換検定（spec×rep 対、10,000再標本、両側 α=0.05）で有意、
  かつ BCa 95%CI が 0 を跨がない。
- **「実質的削減」の事前基準**: 中央値ベースで **≥20%** 削減。
  20% 未満の有意差は「削減は実在するが小さい」とそのまま報告する。

### H2（RQ2・時間の非劣性）

- **予測**: レーン継続の直列化による遅延は限定的。
- **判定**: median(T_C) ≤ median(T_B) × (1 + **δ_time**)。δ_time は
  `non_inferiority.md` で凍結【確定 0.15】。bootstrap BCa 片側CI で判定。

### H3（RQ3・品質の非劣性）

- **予測**: セッション継続は品質を実質劣化させない。
- **判定**: 通過率差（C−B）の片側90%CI 下限 > −**δ_q**。δ_q は
  `non_inferiority.md` で凍結【確定 10pp】。検出力不足の場合の扱いは同ファイル §3。

### H4（RQ4・コストモデルの検証）

事前登録する2チェック:

- **(a) 機構レベル**（S2プローブで判定）: warm 境界の初回呼び出しで
  cache_read ≈ H（反復の中央値が **±10%** 以内）。cold 境界（真のTTL超過）で
  cache_creation ≈ H（同 ±10%）。モデル切替で書き直し発生の再現。
- **(b) 端到端レベル**（本実験で判定）: 仕様ごとの費用比 r = Cost_C / Cost_B の実測が、
  §3 モデルによる予測 r̂ に対し **相対誤差 ±25% 以内**が仕様の**過半数**で成立し、
  かつ優劣の符号（C<B か否か）の予測が**全仕様で一致**する。
- 反証時の縮退先: (a) 不成立 → 【A3】棄却 → 主張を session-affinity-aware へ縮退
  （§3.7。研究は成立し続ける）。(b) 不成立 → モデルの適用限界として §8 に記載。

## 4. 検定ファミリーと主張の決定規則

- 構造: **主要評価は RQ1 の1本**。RQ2・RQ3 は主張成立の**共同ゲート**（gatekeeping 構造の
  ため多重比較補正は行わない。この設計自体を §6.5 に記載する）。
- 中心主張「レーン継続は品質・時間を実質犠牲にせず費用を≥20%削減する」を掲げられるのは
  **RQ1有意 ∧ ≥20% ∧ RQ2成立 ∧ RQ3成立** のときのみ。
- 部分成立はそのまま部分成立として報告する。**スピンしない。**

## 5. 実験単位と対応付け

- 単位: spec × arm × rep。B と C は同一 spec・同一反復番号で対にする。
- 実行: アームは時間帯交互配置（ABBA）、仕様内の実行順はランダム化（§6.5）。
- モデル・CLIバージョンは固定し毎ラン記録（`exclusion_rules.md` §4）。

## 6. パイロットの権限（唯一の未凍結項目）

パイロット（1仕様×2アーム×2反復）が決めてよいのは:

1. **反復数 N**（費用の分散から、RQ1 の検出力 0.8 を目標に算定）
2. ハーネスの不具合修正（計装・実行系。判定規則には触れない）

これ以外（仮説・マージン・除外規則・指標定義）は変更しない。

### A-6（2026-09-02）: 停止条件の発火と、再実行率の分母の確定

- **事実**: S6 完走後に `e1_aggregate.py` を実行したところ、`exclusion_rules.md` §3 の
  停止条件（インフラ起因の再実行率 20% 超）に該当し、**E2 の判定を拒否**した。
  E1 の算出値は **61.7%**（インフラ起因 121 / run 196）。
- **原因の所在**: E1 は分子に**中断イベントの延べ回数**を用いていた。§3 の文言は
  「インフラ起因の**再実行率**が全 run の 20%」であり、意図する分子は
  **やり直しが発生した run の本数**である。両者は一致しない。
  実測では、121 件のうち上位8本の run（各10〜13回中断）だけで **94 件**を占めていた。
  同一 run への繰り返し再試行が延べ回数を押し上げていた。
- **正しい指標での値**: **少なくとも1回やり直した run は 27 / 196 = 13.8%**。
  一度も中断しなかった run が 169 本（86.2%）。**停止閾値 20% の内側**である。
- **アーム間の偏り**: 中断はアームB 66件（54.5%）／アームC 55件（45.5%）でほぼ均等。
  不安定さは両アームに等しく降りかかっており、差分推定に系統的なバイアスを
  持ち込む形にはなっていない。仕様別では `w_two_files` に43件が集中しており、
  アームではなく特定仕様・時間帯に紐づく。
- **§3 が求める手順の履行**: 「停止し、原因（時間帯・ベンダー状態・ハーネス）を
  調査してから再開する。再開時は Amendment Log に記録する」に従い、本項を記録する。
  調査済みの原因と対処は以下（いずれもコミット済み）:
  1. 一過性 429 に対しフレームワークが 60分のローカル遮断を書き込み、以降の全タスクを
     quota exhausted にしていた。`QUOTA_PATTERNS` の裸の `"429"` が `--stream-json` の
     20万文字規模の stdout に部分一致する誤検知も含む。→ API の生死を直接確認して
     遮断のみ解除する運用（`harness/run_window.sh`）。
  2. アーム主体の実行順では上限が来ると必ず対が割れ、対ごと再実行が発生していた。
     → 仕様主体へ変更（A-5）。以後、上限起因の対分割は消えた。
  3. `git worktree` の登録と実体の不整合で `add` が失敗していた。→ 修正済み。
  4. 実際の利用上限（5時間周期）。これは外部要因であり解消できない。待機で対処。
- **判断**: 上記により**データは使用可能**とし、E2 を実行する。
  E1 の閾値判定ロジックは**変更しない**（データを見た後にコードを緩める形を避ける）。
  本項に正しい指標での値を記録し、Results と §8 に併記する。
- **開示**: 本項の起草・記録時点で、**起草者は本実験の B と C の比較値を一切見ていない**。
  E2 は本 Amendment のコミット後に初めて実行する。判断が結果に影響していないことを
  コミットの順序で示す。

### A-5（2026-08-28）: 実行順をアーム主体から仕様主体へ戻す

- **変更内容**: 1反復内の実行順を「全仕様の第1アーム → 全仕様の第2アーム」から
  「仕様ごとに B→C を隣接」へ戻す。あわせて cooldown を 12分から 0 にする。
  **判定規則・指標定義・マージン・除外規則は一切変更しない。**
  ABBA（反復ごとのアーム順反転）も維持する。
- **理由**: 本実験の第1・第2窓で、**利用上限が来ると必ず対が割れる**ことが実測された。
  アーム主体では先行アームが全仕様分完了してから後続アームに入るため、
  途中で上限に当たると先行アームだけが残る。ABBA でアーム順を反転しても
  鏡像で同じ結果になった（rep1 は B が5対、rep2 は C が3対だけ残存）。
  `exclusion_rules.md` §3 により対ごと再実行が必要なので、そのたびに
  完了済みアームを破棄することになり、12窓分繰り返せば損失が積み上がる。
  仕様主体なら上限は**対と対の間**に落ち、対の内部は割れない。
- **副次的な改善**: 対内の B と C の間隔が「他仕様6本分」から「隣接」へ縮まる。
  時間帯・サービス状態の差が小さくなり、対応付けの質が上がる。
- **A5 汚染への対処**: cooldown ではなく **run ごとの nonce** が担う。
  nonce はプロンプト先頭に入るためプレフィックスが最初のトークンから食い違い、
  TTL に関係なくキャッシュ共有が原理的に成立しない。cooldown は元々
  二重の保険であり、nonce 導入後は必須ではない。
- **層の非均質性（Limitations に記載する）**: rep1 の全7対と rep2 の4対は
  アーム主体（対内の間隔が他仕様6本分）で取得済みであり、これらは**残す**。
  rep2 の残り3対と rep3 以降は仕様主体（隣接）で取得する。
  対応付けは (spec, rep) 単位で閉じているため、各対は自身の条件内で B と C を
  比較しており、この非均質性は対内の交絡ではない。ただし対によって
  B/C 間隔が異なる点は §8 に明記する。
- **本実験開始後の追記である。** `rqs_hypotheses.md` 冒頭は本実験開始以降の変更を
  禁じているが、これは判定規則ではなく**実行系の不具合対応**であり、
  §6 が パイロットの権限として認めている「ハーネスの不具合修正（計装・実行系。
  判定規則には触れない）」と同種のものである。判定に関わる項目は一切動かしていない。
  変更前に記録し、変更後のデータと区別できるようにした。

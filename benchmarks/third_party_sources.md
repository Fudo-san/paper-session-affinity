# 第三者作成仕様の調達先調査（2026-07-05）

> 目的: 著者バイアス回避（自作仕様のみで自作手法を評価しない）＋最近傍研究
> CodeTeam との比較可能性の確保。

## 結論（採用方針）

**二層構成**にする:

1. **統制スイート（自作）** — W/N/M/Contended/Scope-error の形状統制。
   RQ4（損益分岐）・RQ5（アブレーション）のメカニズム分析用。内的妥当性担当。
2. **NL2Repo-Bench サブセット（第三者）** — 10〜15タスクを難易度層化抽出。
   外的妥当性＋CodeTeamとのタスク重複による比較可能性担当。

SketchEval は不採用（理由は下記）。

## NL2Repo-Bench（採用）

- 出典: arXiv:2512.12730 "Towards Long-Horizon Repository Generation Evaluation
  of Coding Agents"（2025-12、カットオフ後・Web検索で確認）
- GitHub: **https://github.com/multimodal-art-projection/NL2RepoBench**（公開）
- 構成: Python ライブラリ再現タスク **104件**（9カテゴリ: System Tools / Data
  Processing / Testing Frameworks / Networking / ML 等）、300〜120,000 LOC、
  Easy(26)/Medium(46)/Hard(32)
- タスク形式: **約18,800トークンの自然言語仕様**（プロジェクト説明・依存リスト・
  APIガイド・使用例）→ 空のワークスペースから installable なリポジトリを生成
- 検証: **原プロジェクトの pytest スイートを Docker 再現環境で実行**。
  エージェントは生成時にテスト・スキャフォールド・対象リポジトリへアクセス不可
  → **我々の「隠しテスト」要件と完全同型**

### 我々の実験への適合性

| 要件 | 適合 |
|---|---|
| 第三者作成仕様 | ✓ ベンチ作者≠我々 |
| 隠しテスト（実行ベース品質） | ✓ pytest 実行のみで判定 |
| Python / repo-level | ✓ |
| 仕様→タスク分解の自由度 | ✓ 仕様のみ提供なので我々の Planner/Architect がそのまま使える |
| コスト実験の予算 | △ Hard は 120k LOC 級で高額。**Easy/Medium から層化抽出**する |

### 注意点

- **形状統制はできない**: タスクグラフは我々の Architect が仕様から生成するため、
  W/N 等の形状はタスクに内生的。→ 実現したグラフ形状を事後計測して層別する
  （graph shape metrics は計装済み計画）。形状を統制した因果分析は自作スイート側の役割
- **CodeTeam との数値直接比較は不可**: CodeTeam は Qwen2.5-72B（オープンウェイト）、
  我々は商用 Claude。同一ベンチのタスク重複による**参照比較**に留める（本文に明記）
- Week 1 残作業: リポジトリを clone し、(a) ライセンス (b) Docker ハーネスが
  WSL で動くか (c) タスクあたりの仕様フォーマット を確認

## SketchEval（不採用）

- 出典: CodeS（arXiv:2403.16443, Zan et al.）付属。19リポジトリ・194ファイル・37.1k LOC
- 不採用理由: 主評価が **SketchBLEU（類似度ベース）** であり、我々の
  「品質＝実行ベース（テスト成功率）」の設計と噛み合わない。参照実装との
  n-gram/構造類似は、正しいが異なる実装を不当に低く評価する

## 副次的発見（新規性の追加証拠）

**CodeTeam はトークンコストも壁時計時間も報告していない**（128k context /
8,192 生成上限の記載のみ）。最近傍研究がコストを測っていないこと自体が、
「コストを目的関数に含める」我々の空白の直接証拠になる。
§2.6 新規性マトリクスに反映済み。

# Contended 仕様の設計（v0.1 — 2026-08-03）

> 目的: レーン方式の**代償**（過剰直列化による並列度の損失）を測れる唯一の形状を用意する。
> 現行3形状（W/N/M）では代償が構造的にゼロになるため、提案手法の新規性が実証できない。
> 参照: `SHAPES.md`（park の理由）、`runs/PILOT_RESULT_2026-08-02.md`

## 1. なぜ必要か（park を解除する理由）

現行3仕様では、レーン制約が**一度も追加コストを生まない**:

| spec | レーン構成 | 代償 |
|---|---|---|
| `w_two_files` (W) | 2レーン×1タスク | resume が起きない。C ≡ B |
| `n_db_chain` (N) | 1レーン×2タスク | 2タスクは**依存関係**で直列。レーン制約は追加拘束にならない |
| `m_mixed` (M) | 上記の混合 | 同上 |

つまり現行の実験は「依存で既に直列なタスクのセッションを使い回すと安くなるか」しか
問うていない。それは**自明な操作**であり、査読者は primitive と判定する。

新規性が宿るのは「**独立している（依存がない）のに write-scope が交差する**」場合だけである。
そこで初めて選択が発生する:

- 従来（アームB）: write-scope 交差は動的に待つ。交差しない相手とは**並列実行できる**
- 提案（アームC）: 連結成分ごと1レーンに畳み、**推移的に全部直列化**する。代わりに文脈を再利用する

この交換を測らなければ、「安全構造を局所性構造として再利用する」という主張は実証されない。

## 2. 形状の要件

タスク A, B, C（**依存関係なし**）の write-scope が:

```
A ∩ B ≠ ∅ ,  B ∩ C ≠ ∅ ,  A ∩ C = ∅
```

このとき:

| | 連結成分 | 実行 | makespan | セッション |
|---|---|---|---|---|
| アームB | 使わない。走行中との交差のみ判定 | **A ∥ C** → B | **2単位** | fresh × 3 |
| アームC | {A,B,C} が推移閉包で1レーン | A → B → C | **3単位** | fresh × 1 + resume × 2 |

**アームBは並列度2、アームCは1。**ここが代償である。
アームCはその対価として resume を2回得る（うち3件目は2タスク分の履歴を継承）。

> 順序に対して頑健: スケジューラが B を先に選んでも、A と C が後で並列化されるため
> アームBの makespan は 2単位のまま。

## 3. 対象モジュールの選定

`src/library/`（square-media @ `d4449a0`）を採用する。

| ファイル | サイズ | 主な内容 |
|---|---|---|
| `src/library/schema.py` | 6.9 KB | `LibraryRecord`, `QualityMeta`, 定数群, `compute_library_hash` |
| `src/library/builder.py` | 7.7 KB | `_row_to_record`, `build_library`, `paper_explainer_to_record` |
| `src/library/indexer.py` | 6.2 KB | `_init_schema`, `build_index`, `search_library` (FTS5) |

**選定理由**:
- 3ファイルが同程度のサイズ（6〜8KB）→ タスク所要時間が揃い、並列度の差が makespan に素直に出る
- `src/db.py`(36KB) や `src/ui/app.py`(77KB) を避けることで、1タスクあたりの文脈が
  現行仕様（cache_read 中央値 438k）より小さくなり、費用も抑えられる
- 3ファイルが機能的に隣接しており、「同じファイルを触るが目的は別」という
  **現実的な false sharing** を自然に作れる

## 4. タスク定義（案）

**重要な設計原則: 同一ファイル内でも別の関数を触る。**
これが file 粒度の連結成分が**過剰**である理由の実体であり、現実のリポジトリで
実際に起きることでもある。

### CT-A — LibraryRecord に `language` を追加

- write-scope: `src/library/schema.py`, `src/library/builder.py`
- 触る関数: schema の `LibraryRecord` / 定数、builder の **`_row_to_record`**
- 内容: `LibraryRecord` に `language: str = "ja"` を追加（許容値の定数を定義し検証）。
  `_row_to_record` が行の値から `language` を設定する（欠損時は既定値）。
- 受入: `to_dict()` に `language` が出る／不正値が弾かれる／既存フィールドは不変

### CT-B — `build_library` に `min_relevance` フィルタを追加

- write-scope: `src/library/builder.py`, `src/library/indexer.py`
- 触る関数: builder の **`build_library`**（CT-A とは別関数）、indexer の `build_index`
- 内容: `build_library(..., min_relevance=None)` を追加し、指定時は該当レコードのみ返す。
  `build_index` が同じ基準で索引対象を絞れるよう引数を通す。
- 受入: フィルタ指定時の件数／未指定時は従来と同一／索引件数が一致

### CT-C — `search_library` に `limit` を追加

- write-scope: `src/library/indexer.py`（**単独**）
- 触る関数: indexer の **`search_library`**（CT-B とは別関数）
- 内容: `search_library(..., limit=None)`。正の整数のみ許容、超過分は切り捨て。
- 受入: 件数が limit 以下／不正値で例外／未指定時は従来と同一

**scope の検算**: A∩B = {builder.py} ✓ / B∩C = {indexer.py} ✓ / A∩C = ∅ ✓
→ 連結成分は {A,B,C} の1個。`build_specs.py` の検証ステップで機械確認すること。

## 5. この仕様が同時に検証できるもの（副次的価値）

パイロットで判明した**モデルの不備**（`resume は cache_read を減らすが cache_write を
増やす。write は read の12.5倍高いため、相殺どころか逆転しうる`）を、この仕様は
最も強く検出できる:

- レーン長が **3**（現行の最大は2）→ 3件目は**2タスク分の履歴**を継承する
- 履歴が長いほど以降のターンの書き込み増分が大きくなるため、
  **write ペナルティが累積する様子**が2段階で観測できる

すなわち CT は「代償（並列度）」と「モデルの不備（write増）」の両方を測る。

本実験（14反復 × 2アーム = 28ラン）で **約 $30**。現行予算 $190 に対し +16%。
